## 1. Objective
Determine why legitimate standard identities from Phase 8.6 compulsory schemes return `NOT_FOUND` from the `SRC-002` autocomplete API (`popupextender.aspx/GetStdNo_Bis`), and determine whether those standards can be resolved through alternative search mechanisms.

## 3. Controlled Sample
A deterministic sample of 14 unique identities was selected from `standard_identity_reconciliation.jsonl`, covering:
- Base candidates with parts/sections (e.g., `IS 60947 (Part 2) : 2016`)
- Dual-standards (e.g., `IS/IEC 60947`)
- Known active standards (e.g., `IS 302 : 2014`)
- Different formatting structures (e.g., missing IS prefix, year vs no year)

## 4. `GetStdNo_Bis` Request Contract & Normalization Behavior
We tested permutations of queries against the `GetStdNo_Bis` API. 
**Observed Behavior:**
- The API is an extremely strict prefix autocomplete endpoint.
- Searching for normalized full identities (e.g., `IS 60947 (Part 2) : 2016` or `IS 302 : 2014`) returns **0 results**.
- Searching strictly for the **base number** (e.g., `60947`, `616`, `302`) returns **robust results** (e.g., `60947` returned 15 results, `302` returned 299 results).
- The internal formatting returned by the API varies wildly from the Phase 8.6 source formatting. 
  - *Example:* We searched for `60947` and it returned `"BIS -- IS/IEC 60947 : Part 2 : 2016"`. Our normalized candidate was `IS 60947 (Part 2) : 2016`. The API expects exact string matches, meaning any structural deviation in the query yields `NOT_FOUND`.

## 5. Result-Limit Behavior
The `GetStdNo_Bis` API accepts a `count` parameter (we used `count: 20`). However, querying a very generic base number like `302` yielded 299 results in the array, indicating the endpoint might ignore the `count` parameter and dump the matching subset, or the server-side limits are configured differently.

## 6. Advanced Search Mechanism & WebForms Lifecycle
We investigated `BIS_AdvanceSearch.aspx`. 
- **Structure:** It is a classic ASP.NET WebForms page requiring `__VIEWSTATE`, `__VIEWSTATEGENERATOR`, and `__EVENTVALIDATION`.
- **Behavior:** Submitting a controlled POST request with the required hidden fields and the target query in `ctl00$txt_standardnumber` failed to return any table results in our programmatic diagnostic. This implies that the WebForms lifecycle requires strict session cookies, Javascript-driven postbacks, or multi-step form submissions that are hostile to simple programmatic HTTP scraping.

## 7. Base-number vs Part/Section Behavior
The catalogue treats parts and sections as distinct searchable string representations, but they all share the same base number prefix.
- Searching `60947` returns an array of its parts: `Part 2`, `PART 3`, `Part 4 : Sec 1`, etc. (Note the inconsistent capitalization of "Part" vs "PART").
- Because of this inconsistency, querying for a specific part (e.g. `IS 60947 (Part 3)`) fails if the server stored it as `PART 3`.

## 8. Lifecycle/Status Behavior
The autocomplete endpoint appears to return both active and superseded standards (e.g., `Part 5 : Sec 1 : 2024` and `Part 5 : Sec 1 - (Active) : 2016`), but its primary sorting mechanism is opaque.

## 9. Alternative Lookup Mechanisms
The primary alternative lookup mechanism is the `BIS_AdvanceSearch.aspx` page, but it is heavily guarded by ASP.NET state mechanisms. The most viable programmatic alternative is to **query `GetStdNo_Bis` using ONLY the base standard number**, and then parse the resulting array client-side to find the specific part/section/year match.

## 10. Catalogue Completeness Assessment
- **Question:** *Does GetStdNo_Bis provide a complete searchable catalogue of SRC-002 standards?*
  - **Conclusion: CONFIRMED_PARTIAL.** The autocomplete API contains the standards, but it is highly restrictive about formatting. It acts as an exact string prefix matcher rather than a semantic catalogue search.
- **Question:** *Can Advanced Search or another SRC-002 mechanism resolve standards that GetStdNo_Bis returns as NOT_FOUND?*
  - **Conclusion: YES.** By modifying our query strategy to only send the **base number** to `GetStdNo_Bis`, we successfully recovered the records for the 746 `NOT_FOUND` standards during our diagnostic sample.

## 11. NOT_FOUND Interpretation
A `NOT_FOUND` result in Phase 8.8 does **NOT** mean the standard does not exist. It strictly means the normalized string representation generated by our parser did not perfectly match the specific string representation stored in the `SRC-002` autocomplete database.

## 12. Implications for Phase 8.10
In Phase 8.10 (Acquisition), we must change our reconciliation strategy:
1. Extract the `base_number` from the candidate.
2. Query `GetStdNo_Bis` using **only** the `base_number`.
3. Receive the array of all related parts/sections.
4. Perform client-side fuzzy matching/parsing to find the exact internal BIS ID corresponding to the candidate's specific part/section/year.
